Executive summary

Encouragingly, your north star is already written down. The README lore — The Company, the Nova monopoly, the Company Rate, compliance trades checked at fleet arrival — matches your recap almost point for point. The gap is implementation, not concept, and the pieces that exist are structurally the right pieces (per-element treasuries wrapped in shared "source" objects are exactly the custody pattern a Company NOVA treasury needs; the lazy Clock-based accrual is exactly the no-keeper model travel time needs).

The catch is that what's built is a thin slice — join a universe, get one random planet, upgrade three mines — and it has two economy-breaking bugs and zero test coverage. None of the trading exists yet: there is no NOVA coin anywhere in the sources, no trade module, no DeepBook dependency, and elements can never leave a planet as a wallet Coin<T>. That last point is the quiet blocker — every market mechanic you want depends on a withdraw/deposit bridge that does not exist.

Fix before you build anything on top. Two confirmed criticals (free thorium upgrades, cross-universe reserve theft) plus the free-universe-cap and unbound-refill bugs form a chain that becomes a mint-to-cash-out faucet the moment a wallet-withdraw and a NOVA/SUI pool exist. These are cheap to fix now and load-bearing later — they corrupt exactly the reserve state every future mechanic reads.

The recommended path: (1) harden the existing slice — fix the six bugs, add the ID-binding invariants, write the tests that should have gated the hackathon build; (2) add the coin bridge and the event/snapshot layer that both the markets and the future agents depend on; (3) build NOVA + The Company + the three trade lanes; (4) layer the extended economy (planet differentiation, storage, ships, research, colonization). The design decisions section flags the handful of forks where your intent changes the architecture — the biggest is global vs. per-universe currencies, which the current single-treasury design has effectively already decided for you.

What is built today

Eleven Move modules, ~1,960 lines. The architecture is a three-tier custody model for resources and a capability model for access:

Bootstrap & registry

  • trade_wars — singleton shared TradeWars (universe registry, global source IDs, SUI fee vault) + mirror TradeWarsInfo for cheap reads; GameAdminCap.
  • universe — shared Universe (g×s×p grid, open flag, pre-generated free_planets pool); transferable UniverseCreatorCap.

Resources (custody in 3 tiers)

  • erbium / lanthanum / thorium — three standard Coin types, 9 decimals, frozen metadata, one TreasuryCap each.
  • element_source — global shared wrapper holding each TreasuryCap (the mint monopoly).
  • universe_element_source — per-universe Balance<T> reservoirs, refilled by minting from the global source.

Players & planets

  • overseer — soulbound player object; tracks joined universes, holds PlanetCaps; entry points: vest, join_universe, three upgrade_*_planet_mine.
  • planet — shared Planet (3 mines + 3 Balance stores + coords); PlanetCap ownership.
  • element_mine / mine_configuration_parameters — lazy time-based production; amount = ⌊Δt/1000⌋ · level / production_factor; upgrade cost = base · level.

Off-chain

  • cli/ — admin Node.js (plain JS) bootstrap: publish, create sources, start/refill universe.
  • web/src — React/Vite player dapp; reads planet state via 15-call devInspect PTBs with hand-rolled BCS.

The production loop is genuinely elegant and worth preserving: no per-tick state, no keepers. A mine holds only accounting fields; on extract it computes elapsed production, splits that Balance out of the universe reservoir into the planet store, resets its timestamp, and re-syncs cached config. Upgrade costs flow back into the reservoir — a closed loop, not a burn. That same lazy-Clock pattern is what travel time, build queues, and research timers should all reuse.

The structural gap that blocks everything market-facing. Elements are Coin types, but no code path ever hands a player a Coin<T>. All value lives as Balance<T> locked inside shared Planet stores and reservoirs. There is no withdraw-to-wallet and no deposit-from-wallet function anywhere. Until that bridge exists, DeepBook pools, P2P trades, and agent-held inventory are all unreachable — the coin-standard compliance is nominal, not practical.

Confirmed correctness defects

Nine candidate defects were found; the six below were adversarially verified against the actual code (each reviewer was told to try to refute it). Three more are plausible but unverified — listed at the end. Line numbers are from the current main.

#SevDefectWhere
TW-001Critical Thorium mine upgrades are free. upgrade_thorium_mine asserts affordability and extracts production into stores, but omits the three return_reserves(store.split(cost)) payment lines that the erbium and lanthanum paths have. The mine levels up at zero net cost and the player keeps the extracted resources. Unbounded free leveling — the dominant strategy. planet.move:244–267
TW-002Critical Cross-universe reserve theft. extract_element never checks object::id(source) == self.source. Universe sources are shared, so a player can pass another universe's reservoir into their own upgrade PTB and drain (amount_produced − cost) from it. Repeatable across all three elements; breaks per-universe isolation entirely. element_mine.move:110
TW-003High Anyone can mint into any universe's reservoir. refill_universe_source takes _cap: &UniverseCreatorCap but never validates it against the target source. Any creator cap (free — see TW-005) mints 1,000,000 units into any under-threshold reservoir, and as a side effect overwrites that universe's mine parameters. Combined with TW-002 it is an unbounded farm. element_source.move:37–49
TW-004High close_universe re-opens the universe. Line 216 calls universe.open_universe(cap) instead of close_universe. The authoritative Universe.open flag stays true, so join_universe (which only checks that flag) keeps accepting players by object ID after the creator "closes" it. universe::close_universe has zero callers. trade_wars.move:216
TW-005Medium public_start_universe never checks the public_universe_creation flag, and no setter exists to toggle it (permanently false, unenforced). TW-006Medium Universe fees are permanently locked. Payment is joined whole into universe_creation_fees (no change returned on overpayment) and no withdrawal function exists anywhere. Any SUI collected is irrecoverable without a package upgrade. trade_wars.move:163
Three more plausible defects (not adversarially verified)
  • Med TW-007 — Accrual can permanently brick a mine. amount_produced grows unbounded with time·level while extract demands the full accrued amount atomically (no clamp-to-reserves). A high-level mine idle long enough accrues more than the reservoir can ever hold (~1.5M at defaults); every subsequent upgrade then aborts ENotEnoughReserves forever. element_mine.move:110
  • Low TW-008 — Div-by-zero on production_factor = 0. MineConfigurationParameters has no validation and the admin setter accepts 0; once synced, every read and upgrade for that element aborts. element_mine.move:93
  • Low TW-009 — No bounds on universe dimensions. A 0 in any dimension makes the first join abort on empty pop_back; large dims (255³ ≈ 16.5M) eagerly materialize past gas/object limits. universe.move:295

The four-bug chain. TW-005 (free creator caps) → TW-003 (mint into any reservoir) → TW-002 (drain any reservoir into your planet) → TW-001 (free thorium on top). Individually annoying; together, once a wallet-withdraw and a NOVA/SUI pool exist, a scheduled agent turns fabricated element wealth into real money. Fix the whole chain before opening any coin egress.

NOVA & The Company

Superseded by architecture-spec.html. The Company is now sell-only with an EMA-price + depth controller and per-element market shards; there is no vault, no buy side and no constant-product curve. Bought elements are recycled.

The architecture decision this pillar forces

NOVA and elements are Move types: one package, one type, one TreasuryCap. Per-universe NOVA as distinct types is impossible without publishing a package per universe. The current code already implies the resolution: supply is global, production is per-universe. Universe reservoirs stay as rate-limiters on element creation, not economic borders. This is what makes single global DeepBook pools and one NOVA liquidity base coherent.

Proposed modules

  • nova. OTW + coin::create_currency<NOVA> (9 decimals to match elements), freeze metadata, hand the TreasuryCap to company::found_company in the same publish PTB. Plain Coin, not sui::token (rationale below). NOVA lives in wallets as a normal coin.
  • company. A one-shot, admin-gated found_company (mirrors create_element_sources) creates a shared Company holding the NOVA TreasuryCap, per-element vaults, per-element RateState (TWAP), a premium_bps (e.g. 750 = +7.5%), an epoch mint cap, and an optional DeepBook pool registry. No admin mint entry exists — supply is purely algorithmic: mint-on-sale, burn-on-fuel.

Element → NOVA sale (works day one, DeepBook-independent)

Because the Company mints NOVA, a fallback sale can price against a virtual constant-product curve per element with no real NOVA inventory: sell_element<T>(company, payment: Coin<T>, min_out) → Coin<NOVA>. Price falls as players dump an element (this is the dynamic Company Rate), a time-decayed EMA is updated on each trade (the manipulation-resistant rate compliance trades read), and no NOVA input is required — satisfying the "stations near every planet" lore. Keep it public fun returning a Coin so PTBs compose. This curve stays permanently as the guaranteed-liquidity anchor even after DeepBook pools exist.

Enforcing the NOVA burn

Burn is enforced at point-of-use, not at the token layer: every travel function takes fuel: Coin<NOVA> by value and ends with company::burn_nova(company, fuel). Since only the Company holds the cap and Coin has no drop, burning is the only legal way those functions can dispose of the fuel. Overpaid fuel splits exact and returns change (do not repeat the keep-the-whole-coin bug from public_start_universe).

Verdict on sui::token: use plain Coin for both elements and NOVA. Token<T> is key-only — it cannot enter a DeepBook BalanceManager or sit in a Balance-based struct, so adopting it kills the DeepBook pool vision and the NOVA→SUI play-to-earn leg. The one thing it buys (protocol-enforced spend/burn) you already get with plain Coin, because the burn happens inside game functions that take the coin by value and hold the only TreasuryCap. Reserve sui::token for a future soulbound resource (e.g. research points) that must never be tradable.

The three trade lanes

Superseded by architecture-spec.html. Lane 1 is not a DeepBook pool but the Company sell function; Lane 3 snapshots its rate at launch and settles against escrows and inbound as well as on-hand; the premium is a defender-favourable skew. Lanes B and C carry a level-band check.

The DeepBook design below is grounded in the local checkout at deepbookv3/packages/deepbook — real API surface, not assumptions.

Lane 1 — Element → NOVA via DeepBook

Convention: all pools are Pool<ELEMENTx, NOVA> (element = base, NOVA = quote). Because elements are globally fungible, one set of three pools serves all universes. The player path needs no custom trade code:

// player PTB
let erb: Coin<ERBIUM> = overseer::withdraw_element<ERBIUM>(...);
let (change, nova, _deep) = pool::swap_exact_base_for_quote<ERBIUM, NOVA>(
    pool, erb, coin::zero<DEEP>(ctx), min_nova_out, clock, ctx);

Two verified DeepBook gotchas that shape the design. (1) On game pairs you must pass coin::zero<DEEP>() and pay_with_deep = false — a whitelisted DEEP reference pool can never exist for NOVA/elements, so any DEEP-fee path aborts ENoDataPoints. Fees are then input-token at taker_fee × 1.25; budget that into market-maker spreads. (2) pool::mid_price is a public view but aborts on an empty book side (EEmptyOrderbook) and is not depth-weighted — one 1-lot order at an extreme tick moves it arbitrarily. This is exactly why compliance rates route through a stored TWAP, never spot. Pool creation costs exactly 500 DEEP each, tick sizes must be powers of ten.

Lane 2 — P2P element-for-element (custom, burns NOVA)

Each offer is its own shared object (no central hot Table): TradeOffer<Offered, Wanted> holding an escrowed Balance<Offered>, want amount, origin coords, expiry. create_offer withdraws from the seller's planet store (settling production first) into the escrow. accept_offer takes the buyer's payment + fuel: Coin<NOVA>, asserts fuel ≥ round_trip_fuel(distance), burns the fuel, and — crucially — goods do not teleport: it mints two Shipment objects that arrive after Δt = distance × ms_per_distance and are claimed into the destination planets via a permissionless deposit. Buyer pays full round-trip fuel regardless of outcome (per README). Expired offers get a permissionless sweep so shared-object litter is bounded.

Lane 3 — Compliance Trade (the "attack")

The Sui-native framing: an enforced trade is a public function on the target's shared Planet that deliberately performs a cap-less mutation, gated only by economic conditions. Two phases honor "rate checked at arrival":

  1. launch — burns fuel immediately (the NOVA at risk), escrows the attacker's payment sized at demanded × rate × safety_margin (e.g. 150%, because the binding rate is read later), creates a shared ComplianceFleet with arrival_ms, and emits ComplianceLaunched so the target sees it coming — the negotiation window the premium is designed to encourage.
  2. execute (callable by anyone after arrival) — reads the cross-rate from the TWAP feeds (rate(Pay→Want) = twap(NOVA/Want)/twap(NOVA/Pay) × (1 + premium), rounded in the Company's favor), then settles against the target's on-hand store only. Success pays the target and ships goods back to the attacker; failure (target liquidated the resource, or rate moved past the escrow) returns the escrow and the launch fuel is already gone — wasted, exactly as specified. Target's "spend before arrival" dodge works automatically because the store is checked at landing.

Griefing is the sharpest balance risk here. Repeated attacks can strip a new player's only planet, and the play-to-earn leg lets a whale buy attack fuel with SUI. Newbie-immunity window, per-target cooldown, and a max-fraction-per-landing cap are not optional polish — they are the difference between "enforced trading" and "wallet-draining harassment." These are pure game-balance numbers only you can set.

Resource & progression economy

Superseded by architecture-spec.html. Direction unchanged and adopted. Numbers and the emission model (demand-gated, per-planet weighted quota) are in the spec's Production and Tokens sections.

Diagnosis of the current economy

Production p(L) = L/5 units/s, cost base·L (linear), so payback ≈ 50L seconds and levels grow O(t), cumulative supply O(t²) — a pure faucet with no sinks and no meaningful choices (all three elements identical, all planets identical, and thorium is free). The redesign must bend cost geometric, cap accrual, differentiate planets, add real sinks, and drop the manual refill keeper — all while staying lazy.

Foundation fixes (prerequisites)

  • Fix the three missing thorium return_reserves lines (or refactor all three upgrades into one pay_costs helper).
  • Add universe: ID to Planet; assert source.id == mine.source and source.universe == planet.universe everywhere; bind refill caps to their universe.
  • Kill truncation loss — accumulate accrual in milli-units and carry the remainder, so frequent small extracts stop yielding zero.
  • Resolve decimals: scale all constants by 1e9 (wallet-friendly) or redeploy at 0 decimals — before any pool exists.

New mechanics (each stays lazy)

  • Storage = bounded accrual: effective = min(produced, capacity − stored). This single clamp also fixes the mine-bricking bug (TW-007).
  • Planet differentiation rolled at claim time: primary/secondary/poor element richness in basis points; ~30% chance a slot is exactly 0 → that planet cannot mine that element and must trade.
  • Build slots & lazy construction queue: each building level consumes a field; start_build pays now, claim_build after ready_at. Time-gates progression independent of raw wealth.
  • Ships (Shipyard-gated) = trade capacity; the largest element sink — route ship/research costs to burn, keep mine/storage costs recycling.
  • Research per-overseer-per-universe: extraction, cargo, astrophysics (gates colony count), nova-efficiency, compliance-shield.
  • Colonization: cap = 1 + astrophysics_level; cost curve lives in a geometric NOVA burn per additional planet; abandon_planet returns coords so universes never exhaust.

Emission without a keeper

Replace the manual refill_universe_source with a permissionless lazy drip: the reservoir gains last_drip_ms, drip_rate_per_s, max_reserves; any player whose extraction would fall short simply prepends a drip_refill call in their PTB. Universe inflation becomes an explicit tunable schedule instead of an ops process, and the global source is touched only opportunistically. Net inflation = drip − incineration, both observable on-chain.

An extra "trade-not-battle" mechanic worth considering: Supply Contracts. A planet posts a standing on-chain order (element X for Y at ratio R, secured by escrow); others fill it by shipping (NOVA burn applies). It is the PvE-free demand generator that makes richness-zero planets viable, and it gives the Compliance Trade a clean definition: "forcibly filling someone's unposted contract at the pool cross-rate + premium."

Decisions only you can make

Superseded by architecture-spec.html. All seven are decided. Each card below now carries the decision as of 2026-09-20; the leanings are kept to show what changed.

These forks change the architecture, not just the numbers. I have put a recommendation on each, but they hinge on your intent, so they are the first things to settle before the build phase. I will bring these to you as explicit questions before writing code.

1. Coin egress model — the single biggest fork

Do elements leave planets as wallet-held Coin<T> (required for DeepBook element pools and agent inventory), or does all trading operate on planet-store Balances through game modules only (tighter control, but DeepBook reduces to NOVA/SUI pairs and the Company must bridge store-balances to pool liquidity)?

Leaning: wallet-held coins with a withdraw/deposit bridge — it is what the whole vision rests on. But it commits you to a global element economy (next question).

Decided: Withdraw-only. Wallet Coin<T> exists only to sell to the Company; no deposit path at all (type-flow invariant, R2). Trading operates planet-store to planet-store through game modules.

2. Global vs. per-universe economies

The current single-TreasuryCap design makes ERBIUM globally fungible, so one set of NOVA pools serves everyone. Keeping per-universe economies would require per-universe wrapped tokens — a major rework that contradicts the existing design.

Leaning: accept global supply / per-universe production. Universes stay production shards; the market is one galaxy-wide venue. This matches "NOVA price for everyone."

Decided: Global supply, per-universe production. As leaned.

3. Compliance dodge vs. lock

When a fleet launches, can the target freely spend the demanded element before arrival (dodgeable attack, attacker's fuel wasted — OGame fleet-save flavor), or is a portion frozen at launch (stronger aggression, but a cheap asset-freeze grief)? Middle option: failed arrival still takes min(store, demanded) as a partial fill.

Leaning: no-lock + dodgeable, with meaningful fuel cost as the attacker's risk. Simplest and least griefable; revisit if attacks feel toothless.

Decided: No lock, fully dodgeable, launch fuel burned on a miss. Settlement basis widened to escrows + inbound + pending output (R4) so parking stock elsewhere is not a free dodge.

4. Element subsets — hard zero or soft scarcity?

Should ~30% of planets be unable to mine a given element (maximizes forced trading — the game's thesis), or only have low richness (softer, no one is ever stranded)? Hard zero can strand early players before markets have liquidity.

Leaning: hard zero, but guarantee first-join planets all three elements so newcomers bootstrap before depending on the market.

Decided: Soft scarcity for the first planet (mines all three); colonies may roll a hard zero.

5. Who receives the compliance premium?

The target (compensation, softens attacks), The Company vault (a NOVA/element sink, lore-consistent monopoly rent), or burned? This materially changes attack incentives.

Leaning: split — cross-rate to the target, premium slice to the Company as a sink. Tunable later.

Decided: Nobody. It is a price skew in the defender's favour — a BATNA, not a routed fee. Self and same-overseer raids are forbidden.

6. Sybil stance on Overseers

vest_overseer is free and unlimited, so "one planet per universe" and colony caps mean nothing against an agent minting 1,000 overseers. Is multi-account accepted as inevitable, or should minting be made scarce (SUI fee, one-per-address registry)?

Leaning: a small SUI fee or per-address gate — otherwise every scarcity mechanic downstream is decorative, and the agentic angle makes farming trivial.

Decided: Free commander, first universe free, NOVA fee per further universe. Anti-farm gate is per-planet emission share weighted by planet age + cumulative production; a level-band interaction rule blocks alt-boosting and bullying. No bond, no fee, no registry (decided 2026-09-20).

7. Session cadence & pacing target

Cost-curve steepness and drip rate depend on whether this is hours-to-mid-game (hackathon demo, ~1.2× per level) or weeks (OGame pacing, ~1.5×). What check-in cadence are you designing for — hourly, daily?

Leaning: daily check-in with agent automation filling the gaps — but this is entirely your call and sets every economy constant.

Decided: Daily check-in + agents, ~1.5× geometric cost curve. As leaned.

Lower-stakes knobs to settle during the build: fuel formula shape (flat vs. cargo-scaled), storage-overflow semantics (halt vs. loss), colony targeting (random vs. chosen coordinates), research scope (per-universe vs. account-global), ships as planet-bound vs. Kiosk-tradable NFTs, and DEEP sourcing / target network for pool creation.

Recommended sequencing

Superseded by architecture-spec.html. Phase structure adopted. Phase 1 has no deposit_element; Phase 2 has no element pools and is gated on red-team items R1–R4; the CLI, MCP server and the Claude Code mod are Phase 3 heads on one core.

Four phases. Each ends at a state that is coherent and testable — you never carry a half-wired mechanic across a phase boundary.

Phase 0 — Harden the existing slice

  • Fix TW-001…TW-006 and the three unverified defects.
  • Add the economy invariants: universe: ID on Planet, source-ID and universe-ID asserts on every extract/upgrade/refill.
  • Resolve decimals now (scale constants or redeploy at 0 decimals).
  • Write the test suite the hackathon skipped — the current file is a 6-line stub. This is the "battle-tested" bar you named; nothing else should ship until it exists.

Phase 1 — Foundations for markets & agents

  • Coin bridge: withdraw_element / deposit_element, plus a standalone harvest.
  • Event layer + snapshot views + preflight quotes + idempotency guards.
  • Promote player mutators to composable public fun with receipts.
  • Lazy drip refill; storage caps (which also retire the mine-brick bug).

Phase 2 — The market

  • nova + company (virtual-curve sale live from day one).
  • DeepBook pools (Lane 1) + TWAP feeds + optional Company market-making.
  • trade_port (Lane 2) with shipments and NOVA burn.
  • compliance (Lane 3) with launch/arrival/execute and the griefing guards.
  • NOVA/SUI + NOVA/USDC pools — the play-to-earn leg, near-zero game code.

Phase 3 — The full game

  • Planet differentiation, build slots, ships, research, colonization.
  • Optional Supply Contracts mechanic.
  • Then, and only then: the CLI (fresh in TypeScript — the current one is plain JS) and the MCP server on top of the now-agent-ready API.

Why this order. Every market and agent mechanic depends on the coin bridge and the event/snapshot layer (Phase 1), and those in turn depend on the invariants and tests (Phase 0). Building NOVA before the four-bug chain is closed would ship a money printer; building the CLI/MCP before the API is agent-ready would mean rewriting both against a moving contract. The dependency graph, not preference, dictates the sequence.
